## 2026-08-24〜27: 初期構築〜現在

### 出発点の考え方
超初心者（ルールを全く知らない人）が、ゲーム感覚で麻雀を覚えられるアプリが欲しい、という相談から開始。最初から「実践」を教えるのではなく、「牌の名前を覚える」→「面子を見分ける」→「役を覚える」という積み上げ式の設計にした。ランダム出題で同じ問題の繰り返しを避け、XP/レベルで達成感を出す方針。

### 公開方式の制約と意思決定
Webアプリとして公開したいが、実ログイン（Google認証等）はClaude Artifactのサンドボックス（外部スクリプト・外部API通信をほぼ全面ブロック）では実装不可能と判明。代替として「ニックネームによるローカル記録分け」を提案し採用。この制約は今後Artifactで何か作るたびに再確認する必要がある。

### 二重ファイル管理という技術的負債
`mahjong_gakushu.html`（ローカル確認用・完全版）と`mahjong_gakushu_web.html`（Artifact公開用・フラグメント版、牌画像はBase64埋め込み）はロジックがほぼ同一だが完全に別ファイル。理由は「Artifactは外部ファイル参照ができない」という制約のため。毎回Node一時パッチスクリプトで機械的に差分適用する運用で対処しているが、根本的には二重管理であることに変わりはない。将来的にビルドスクリプトで自動生成する方式に変えるのも一案。

### ルール精度への強いこだわり
ユーザーは麻雀ルールの正確さに非常に厳しい。両面待ちの片側だけ正解扱いにしていたバグ、混一色/清一色の排他条件の誤り、大三元判定が同じ牌の刻子重複を許してしまうバグなど、いずれもユーザー自身が見抜いて指摘した。以後、ランダム生成ロジックを書くときは「実際のルール上の制約を先に洗い出してから実装」「大量生成して矛盾がないか自己検証」を徹底するようにしている。

### 段階的な機能拡張の流れ
1. 用語解説・役の早見表を追加（フリガナ・14枚の完成形表示・牌画像つき）
2. リーチ・ドラ・フリテンを「参考情報」として追加 → ユーザーから「クイズ生成エンジンにも組み込めないか」と要望され、出題ロジック本体に統合（参考情報だけでは不十分、実装統合まで期待されると学んだ）
3. 「何切る？」ステージが「面白くない」と却下され、実際の牌をクリックして選ぶ形式に作り直し。さらに「風牌を切れば正解」という表面的パターンに偏りすぎていると指摘され、出題比率を調整
4. 苦手復習モード・初回チュートリアルを追加
5. 携帯での閲覧時にキャッシュが更新されない問題に対応 → クエリ文字列を使った1回限りの強制リロード機構＋手動更新ボタンを実装（localStorageの進捗は保持されることを確認）
6. 「通算正答率は意味が薄い」という指摘を受け、「直近20問のローリング正答率」「レベル進捗バー」「ステージ習熟バッジ」に置き換え
7. 用語解説をさらに拡充（牌の全種類表示、三元牌・風牌・役牌の解説、聴牌を13枚の実例で表示、両面待ち/カンチャン待ちの？マーク位置を実際の待ち方に合わせて修正、役の併用ルール解説を新設）
8. 中級者向けステージ⑧「危険度を見抜く」を追加。筋・壁などの確率的な安全度は扱わず、フリテンのルールで100%断定できる「現物」だけを扱う設計にした（このアプリの他のクイズと同じく「必ず1つに断定できる」出題であることを優先）
9. 「写真から点数計算したい」という要望 → Artifactでは外部API通信ができないため、別のローカル専用ツール`mahjong_score_scanner.html`として新規に作成。Gemini APIで牌を画像認識し、独自の手牌分解アルゴリズム（バックトラック法で4面子+雀頭/七対子/国士無双の全パターンを列挙し最高得点を採用）で役・翻・符・点数を計算。実際のルール上の点数表と一致することをNode単体テストで検証済み（平和ロン30符1翻=1000点、七対子2翻25符=1600点、大三元役満=32000点、満貫ツモ2000/4000=8000点、など）

### Gitでの納品フロー
リポジトリ（[kenny19790413/tool-dev](https://github.com/kenny19790413/tool-dev)）はdejiina_agent以外にも無関係な複数プロジェクトが同居する共有ワークスペース。`git add -A`は絶対にせず、そのセッションで自分が触ったファイルだけを明示的に指定する。masterがデフォルトブランチのため、まずfeatureブランチにpushし、ユーザーの明示的な承認（「お願いします」）を得てから`master`にfast-forwardマージ・pushする、という二段階フローを踏んでいる。

### 判明した重要な仕様（Artifactの公開共有の挙動）
Artifactを「Anyone with the link」で公開共有すると、Share画面の「Shared version」が**その時点のバージョンに固定（ピン留め）**され、以後いくら中身を更新・再公開しても、共有リンクを見る人には自動反映されない。回避策は「Only you」に一旦戻す→「Latest」を選択→「Anyone with the link」に戻す、という手順だが、この手順も**実行した瞬間のバージョンに再度固定される**（動的な「常に最新」設定は存在しない）。つまり、更新するたびに毎回この3ステップを繰り返す必要がある。これは今のところ回避不可能なプラットフォーム側の仕様であり、ユーザーがAnthropicへフィードバック済み。**今後Artifactを更新するたびに、この手順を実行するようユーザーに伝える必要がある。**

## 2026-08-27（続き）: 初心者〜上級者への拡張

ユーザーから「初心者にもっと優しく、中級者・上級者にも使えるように発展させるには？」と相談を受け、レベル帯別に4つの拡張案を提示 → 全て採用され、以下を実装。

1. **役の併用クイズ化**（低コストな改善）: 直前に追加した「役の併用ルール」参照データ（併用できる例・できない例）をそのままステージ④の出題に流用。新しいデータ構造を増やさず、既存データの再利用だけで実現できた良い例。
2. **ミニ実演モード（初心者強化）**: 1局の流れ（配牌→ツモ→打牌→…→和了→点数計算）を、具体的な牌を使ってページ送りで見せるデモ画面を新設。チュートリアル・ホーム画面・用語解説の3箇所からアクセスできるようにした。
3. **筋・押し引きステージ（中級者強化）**: ステージ⑨として新設。「壁」は判定ロジックが複雑になりすぎる（盤面全体の枚数管理が必要）ため参照情報のみにとどめ、クイズ化するのは「筋」（端牌1・2・8・9を切った場合に限定することで、スジ候補が常に1枚に断定できるようにした）と「押し引き」（教科書的に異論のない4パターンのみ扱い、点差・巡目が絡む高度な判断は扱わない）に絞った。ルール精度が命のアプリなので、あいまいな判断が必要な部分は最初から出題対象に含めない、という判断。
4. **牌効率・受け入れ枚数計算（上級者強化）**: これが一番大掛かりで、`mahjong_score_scanner.html`用に作った「14枚の手牌をバックトラック法で4面子+雀頭に分解するエンジン」を`mahjong_gakushu.html`側にも移植し、「13枚の手に1枚加えたら成立するか」を全34種類試すことで聴牌判定・受け入れ牌を求める`tenpaiWaits13()`を実装。出題は「3面子+雀頭+崩れた1組」を意図的に組み立て→14通りの打牌それぞれについてこのエンジンで聴牌判定→**正解が一意に定まる手だけを採用**（最大40回リトライ、だめなら簡易版にフォールバック）、という「生成 → 汎用エンジンで自己検証」の二段構えにした。これにより、シャンテン数の複雑な公式を独自実装するリスクを避けつつ、正確性を確保できた。

**教訓**: 複雑な牌効率・受け入れ枚数のロジックを実装する際、独自のシャンテン数公式を実装するより、「もう1枚あれば完成するか」を全パターン試す力技（ブルートフォース）の方が、実装ミスのリスクが低く、既存の実績あるロジック（decomposeHand系）を再利用できるので安全だった。パフォーマンスも実用上問題なし（1問あたり数十ms）。

## 2026-08-28: ステージ⑨「筋と押し引き」の充実

ユーザーから「筋と押し引きの考え方は面白い、もっと充実させたい」との要望。以下を追加。

1. **筋を全ランク（1〜9）に対応**: これまでは「答えが必ず1枚に断定できる」という設計方針を優先し、端牌（1・2・8・9）のみに限定していた。今回、`answerTileClick`のコア判定を「事前に決めた1つの正解インデックス」から「クリックした牌自身のrole」ベースの判定に変更（`role==="floaterBad"`の牌はすべて正解として扱う）。これにより4〜6を切った場合の「両側スジ」（例：5切りなら2と8の両方が正解）にも自然に対応できるようになった。既存のステージ7・8（正解が1つだけ）への影響がないことも回帰テストで確認済み。
2. **壁を新規クイズ化**: 「ある牌が4枚とも見えている＝もう誰の上がり牌にもならない」という、待ちの種類を問わない絶対的な安全度に絞ることで、これまで参照情報のみだった壁を安全にクイズ化できた。
3. **押し引きシナリオを4→8に倍増**: 複数リーチ・安全牌なしの場合の押し・自分がリーチ後は降りられない（ルール上の制約）、など新しいパターンを追加。
4. **両筋（りょうすじ）を用語解説に追加**。

**教訓**: 「答えを一意に断定できる出題だけを作る」という設計方針を保ったまま出題範囲を広げたいときは、まず出題ロジックではなく「正解判定の仕組み」自体を汎用化できないか検討するとよい。今回は`answerTileClick`の判定方法を変えるだけで、既存コードへの影響なしに新しいバリエーション（複数正解）に対応できた。

## 2026-08-28（続き）: 公開版に点数計算機を内蔵

「点数計算のリンクをしっかり貼ってください」との依頼。実際にはローカル版にはリンクがあったが、公開版（Artifact）には`mahjong_score_scanner.html`（Gemini API使用のローカル専用ツール）へのリンクを一切貼っていなかった——というより、Artifactの仕組み上ローカルファイルへは原理的にリンクできない。この制約をユーザーに説明し、選択肢を提示した結果、「公開版に手動入力版の電卓計算を埋め込む」方針が採用された。

`mahjong_score_scanner.html`の点数計算エンジン（手牌分解・役判定・符計算・点数計算、写真解析部分を除く）をそのまま`mahjong_gakushu.html`/`mahjong_gakushu_web.html`に移植し、新しい画面「🧮 点数計算機」を追加。牌をタップで14枚選び、ロン/ツモ・リーチ・親子・自風場風・ドラを指定すれば、その場で役・翻・符・点数（子/親、ロン/ツモの内訳まで）が計算できる。既存のクイズ用エンジン（`computeYaku`/`HAN_TABLE`など、常にリーチ前提・ロン限定の簡略版）とは名前が衝突するため、移植版は`computeYakuForShape`/`SCORE_HAN_TABLE`など別名にして共存させた。

これで公開版（Artifact）だけでも、外部ツール・APIキーなしで実戦の点数計算が完結するようになった。写真からの自動読み取りをしたい場合は、引き続きローカル版から`mahjong_score_scanner.html`にリンクできる。

## 2026-08-28（続き）: 二盃口の判定バグを修正

ユーザーが点数計算機で「一二三萬×4組＋九九萬の雀頭」（同じ順子が4組）を試したところ、一盃口（1翻）としてしか計算されず、二盃口（3翻）が付かなかった。

原因は`computeYakuForShape`内の二盃口判定：
```js
if(sorted[0]===sorted[1] && sorted[2]===sorted[3] && sorted[0]!==sorted[2]){ ...二盃口... }
```
最後の`sorted[0]!==sorted[2]`という条件が、「4組とも完全に同じ順子（AAAA型）」のケースを誤って弾いていた。二盃口は本来「同じ順子のペアが2組」あれば成立し、AABB型（2種類×2組ずつ）だけでなくAAAA型（1種類×4組＝AAペア2つとして解釈できる）でも成立するのが正しいルール。`sorted[0]!==sorted[2]`を削除し、`sorted[0]===sorted[1] && sorted[2]===sorted[3]`だけで判定するよう修正（AABC型・ABCD型は従来通り正しく除外される）。

このバグは`mahjong_score_scanner.html`・`mahjong_gakushu.html`・`mahjong_gakushu_web.html`の3ファイルすべてに同じロジックがコピーされていたため、3ファイルとも同時に修正した。AABC型（通常の一盃口のみ）・AABB型（二盃口）それぞれで正しく動作することをブラウザで再検証済み。

**教訓**: 同じロジックを複数ファイルにコピーして使う場合、1つのファイルでバグが見つかったら残りのファイルも必ず同時に確認する（`grep`で同一パターンを横断検索すると早い）。今回のような「4組とも同じ」という一見特殊なケースは、ユーザーが実際に手を組んでみて初めて発覚した。ロジックを書く際は「全部同じ」「全部バラバラ」のような極端なケースも意識してテストするとよい。

## 2026-08-28（続き）: 三暗刻のロン/ツモ判定バグを修正・手牌を自動整列

ユーザーから「並び順で間違いが起こらないか再チェックしてほしい。三色同刻と三暗刻はどちらが優先されるか」との依頼。

**確認結果**: 三色同刻と三暗刻は排他ではなく、実際のルール通り両方同時に成立して翻数が加算される（対々和も同様）。ここに優先順位の問題はなかった。

**ただし別の本物のバグを発見**: 三暗刻が刻子3組以上ならロン/ツモの区別なく無条件に成立していた。実際のルールでは、ロンで和了した場合、その和了牌がシャンポン待ちのどちらかの刻子を完成させた可能性があり、その刻子は「明刻」（暗刻に数えない）扱いになる。刻子がちょうど3組のときはロンだと3組とも暗刻か断定できないため、四暗刻と同じ考え方で「ツモの場合のみ」認めるよう修正。ただし刻子が4組（対々和との複合）なら、ロンでどれか1組が明刻になっても残り3組は確実に暗刻のままなので、ロンでも成立するよう条件分岐した（`kotsuCount>=3 && (isTsumo || kotsuCount>=4)`）。3ファイルとも同時に修正し、ロン/ツモそれぞれで正しく動作することを確認。

**手牌の並び順UXも改善**: タップした順に牌が表示されると目視確認がしづらいという指摘を受け、牌を追加するたびに萬子→筒子→索子→字牌・各スート内は昇順、に自動整列するようにした（`sortHandTiles`）。3ファイルすべてに適用。

**教訓**: ユーザーからの「これとこれはどっちが優先？」という質問は、実装に本当にバグがあるサインのことがある。今回は質問された内容自体（三色同刻vs三暗刻の排他性）は杞憂だったが、確認作業の過程で全く別の場所（ロン/ツモの区別漏れ）にある本物のバグを発見できた。役同士の関係を聞かれたときは、その2つだけでなく、同じ関数内の周辺ロジック全体を見直すとよい。
