## 開発中に踏んだハマりどころ（技術メモ）

### プロジェクト移動作業中にgitリポジトリのメタデータを一時的に消失させる事故が発生（復旧済み）

`Move-Item`でリポジトリルート全体（1.2GB、node_modules多数含む）を一括移動しようとしたところ「item is in use」エラーで失敗。原因はBash/PowerShellツール自身のカレントディレクトリが移動対象内にあり、Windowsのプロセスハンドルロックがかかっていたこと。`Start-Job`で独立プロセスから再実行したところ、**`.claude`, `.firebase`, `.git`, `33_SNSハーネス`の4フォルダだけが移動され、残りは移動されないまま処理が終了する**という中途半端な状態になった。

これを「移動失敗」と判断し、移動先フォルダを`Remove-Item`で削除してクリーンアップしたところ、**実際には`.git`フォルダの中身（HEAD/config/objects/refs等）とルート直下の一部ファイル（`.gitignore`, `LICENSE`, `README.md`, `index.html`, `kakeibo.html`, `manga.html`, `bucket-list.html`, `firebase.json`等14件）は、その時点で既に移動先に正しくコピーされ、移動元からは削除済みだった**。つまり削除したのは「失敗の残骸」ではなく「正常に移動済みだった一部」であり、結果的にこれらのファイル・gitメタデータが両方の場所から失われた。

**復旧手順**: このセッションで行った全コミット（`df0e54c`まで）はGitHubにpush済みだったため、実データの損失はなかった。
1. `git init` → `git remote add origin ...` → `git fetch origin`
2. `git symbolic-ref HEAD refs/heads/master` → `git reset origin/master`（`--hard`は使わず、ワーキングツリーは保持）
3. `git status`で「D」表示された、git管理下だが実ファイルが欠落しているものを`git checkout origin/master -- .`で一括復元
4. 旧パス・新パスの全ファイル一覧を`find`で突き合わせ、欠落0件・復元14件（上記の消失分と一致）を確認して裏付け

**教訓**: 大容量ディレクトリの移動は、`Move-Item`のような「コピー後に元を消す」操作ではなく、①`robocopy`等でまずコピーのみ実行し、②コピー結果を突き合わせ検証してから、③最後に元を削除する、という3段階に分けるべきだった。特にツール（Bash/PowerShellセッション）自身のカレントディレクトリが移動対象に含まれる場合は要注意。

### `robocopy`は`node_modules`内のpnpmシンボリックリンクで異常に遅くなる・数が合わなくなる

`33_SNSハーネス/x-harness-oss`がpnpmを使っており、`.pnpm`ストア配下に大量のシンボリックリンクを持つ。これを含めて`robocopy`で丸ごとコピーすると、シンボリックリンクが実体化されて重複コピーが発生し、コピー先のディレクトリ数が元より2000件以上多くなる現象が発生した。**`node_modules`と`.next`は`/XD`オプションで除外し、移動後に各プロジェクトで`npm install`し直す方針に切り替えて解決**（そもそもこれらは.gitignore対象のビルド成果物であり、移動する必要がない）。

### `.git`が壊れているかは`git status`の`D`（deleted）表示で見分けられる

`git reset <ref>`直後に特定のファイルが`D`と表示される場合、「そのファイルはgitの記録上は存在するはずなのに、ワーキングツリー上に実体がない」ことを意味する。今回はこれを手がかりに、消失したファイルがすべてgit管理下にあり`git checkout`一発で復元できると判断できた。逆に`??`（untracked）のまま消えているファイルがあれば、gitでは復元できない実データ損失を意味していた（今回は該当なし）。
